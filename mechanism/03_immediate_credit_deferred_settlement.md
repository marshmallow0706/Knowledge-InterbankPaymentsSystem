# 第3章　即時入金と後決済 — 通知と資金の分離

[← 前章](02_relay_computer_and_network.md)　｜　[目次](README.md)　｜　[次章 →](04_multilateral_netting_ccp.md)

---

## 3.1 設計の核心

全銀システムの小口取引は、次の2つを **意図的に分離** しています。

| | 為替通知（情報） | 資金決済（お金） |
|---|---|---|
| タイミング | 取引ごとに **即時** | 1日1回 **16:15** にまとめて |
| 単位 | 1件ずつ（グロス） | 清算参加者ごとの差額（ネット） |
| 受取人への効果 | 着信と同時に入金 | — |
| 銀行の日銀当預 | 動かない | 差額だけ動く |

## 3.2 なぜ分離するのか

もし1件ごとに銀行間の資金を動かす（すべて RTGS にする）と、

- 1日数百万件の取引ごとに日銀当座預金を動かす必要がある
- 各銀行は1日の支払総額に近い流動性（当座預金残高）を常に手元に置かなければならない
- 残高が足りなければ振込が止まる（支払待ちが連鎖する「グリッドロック」）

一方、差額だけを決済すれば、必要な流動性は **グロス総額のごく一部** で済みます（模擬では 90% 前後の圧縮。→[第4章](04_multilateral_netting_ccp.md)）。
その代わり、通知と決済の間に「未決済の債権債務」が残ります。

## 3.3 未決済の間に何が残っているか

10:00 に あおば銀行 → つばさ銀行 へ 5万円 の振込があったとします。

```mermaid
flowchart LR
  subgraph 10:00〜16:15
    A[あおば銀行] -- "5万円の支払義務" --> Z[全銀ネット<br/>CCP]
    Z -- "5万円の支払義務" --> T[つばさ銀行]
  end
  T -->|すでに入金済み| B[受取人Bさん]
```

- つばさ銀行は、自分の資金で Bさんに入金済み（顧客に対しては後で取り消せない）
- その一方で、つばさ銀行が全銀ネットから資金を受け取るのは 16:15
- 全銀ネットが CCP として間に入ることで、つばさ銀行の相手方は「あおば銀行」ではなく「全銀ネット」になる（→[第4章](04_multilateral_netting_ccp.md)）

このリスクを管理するのが **仕向超過限度額**（未決済の支払超過額の上限）と、決済不能時の **流動性供給・担保** です（→[第7章](07_settlement_guarantee_and_default.md)）。

## 3.4 銀行内部の会計（概念）

仕向銀行・被仕向銀行の内部では、16:15 まで「未決済」の勘定で管理されます（科目名は概念的なもの）。

| タイミング | 仕向銀行 | 被仕向銀行 |
|---|---|---|
| 振込時 | 借方 預金（依頼人）／ 貸方 未決済為替（支払） | 借方 未決済為替（受取）／ 貸方 預金（受取人） |
| 16:15 | 借方 未決済為替（支払）／ 貸方 日銀預け金 | 借方 日銀預け金 ／ 貸方 未決済為替（受取） |

実際には各取引ではなく差額で日銀預け金が動き、未決済為替勘定はすべての取引を合わせてゼロになります。

## 3.5 大口取引は逆の順序

1億円以上の大口取引は、**資金決済（RTGS）が先、為替通知が後** です（→[第5章](05_large_value_rtgs.md)）。
金額が大きいため、未決済のまま入金させるリスクを取らない設計です。

| | 小口（1億円未満） | 大口（1億円以上） |
|---|---|---|
| 順序 | 通知 → 入金 → … → 16:15 決済 | RTGS 決済 → 通知 → 入金 |
| 未決済リスク | あり（限度額・担保で管理） | なし |
| 必要な流動性 | 差額分 | 全額 |

## 3.6 模擬システムで確かめる

```bash
python -m unittest tests.test_system.FlowTest.test_small_transfer_and_settlement
```

このテストは「振込直後に受取人の残高は増えているが、日銀当預はまだ動いていない」「16:15 を過ぎると差額だけ動く」ことを検証しています。
ダッシュボード（`python -m zengin_sim serve`）でも、振込後に口座残高は変わるのに日銀当預が動かず、16:15 に一斉に動く様子が見られます。
