## 10.1 年表

| 年 | 出来事 |
|---|---|
| 1973年4月 | 全国銀行内国為替制度発足、**全銀システム稼働**（第1次）。即時入金を実現 |
| 1979年〜2003年 | 第2次〜第5次全銀システム（概ね8年周期のレベルアップ） |
| 1988年 | 日銀ネット稼働 |
| 2001年1月 | 日銀当座預金決済の RTGS 化と同時に、内国為替制度の CCP を日本銀行から東京銀行協会へ変更。決済リスク対策（仕向超過限度額・担保等）を強化 |
| 2004年3月 | 全銀協が大口決済の日銀ネット集約を提言 |
| 2010年 | **全銀ネット設立**、資金清算機関として制度・システムの運営を承継 |
| 2011年11月 | 第6次全銀システム。1億円以上の大口取引を日銀ネットで RTGS 決済 |
| 2018年10月 | **モアタイムシステム稼働**（24時間365日の即時振込） |
| 2018年12月 | 全銀EDIシステム（ZEDI）稼働 |
| 2019年 | 第7次全銀システム |
| 2020年 | 公正取引委員会報告、成長戦略実行計画で銀行間手数料・参加資格が政策課題に |
| 2021年10月 | 銀行間手数料を廃止し **内国為替制度運営費（62円）** を創設 |
| 2022年 | 参加資格を **資金移動業者に拡大**。ことら（少額個人間送金）開始。電子交換所稼働 |
| 2023年10月 | RC 更改時に **初の大規模障害**（→[第9章](09_incidents_and_bcp.md)） |
| 2025年 | 全銀ネットが官民有識者による「資金決済システムの将来像に関するスタディグループ」を設置 |
| 2026年3月 | スタディグループ報告書を公表。現行に代わる **「新たな決済システム」構築の方針**（2030年稼働目標） |
| 2026年度中 | 新決済システムの構築是非を最終判断する予定 |
| 2027年 | 第8次全銀システム稼働（予定） |

## 10.2 現行システムの課題

2026年3月の全銀ネット報告書・関連報道で挙げられた課題（要旨）:

| 課題 | 内容 |
|---|---|
| レガシーアーキテクチャ | 設計が古く、新しい利用者ニーズに対応した機能追加が難しい |
| コストの高止まり | 維持コストが高く、部分改修を重ねるほど複雑化 |
| 国際標準・規制対応 | ISO 20022 等の国際標準や、マネロン対策等の規制要請への対応負担 |
| 海外接続 | 海外のリアルタイム決済基盤との相互接続が見通しにくい |
| 新しい決済手段 | トークン化預金・ステーブルコイン等との連携が困難 |

## 10.3 「新たな決済システム」の基本構想（2026年3月公表）

| 項目 | 方針（公表内容の要旨） |
|---|---|
| 位置づけ | 現行システムの部分改修ではなく、課題を抜本的に解決する新システム |
| 稼働目標 | **2030年** |
| 判断 | 2026年度に要件・設計を詰め、2026年度中に構築是非を判断 |
| 現行との関係 | 当面は **現行全銀システムと併存**。稼働時点では現行には原則手を加えない。将来は一部または全部の代替も視野 |
| Day1 の機能 | 送金金額に **上限** を設ける方向。**事前口座確認**、**着金確認** に対応。**携帯電話番号等による送金** も検討 |
| リアルタイム性 | 即時に着金を確認できるリアルタイム決済機能 |
| 新技術との関係 | トークン化預金の発行・償還機能は本体に組み込まない方針。将来の普及に備え、異なる銀行間の授受の共通基盤を想定し、電文の開発・変更に柔軟に対応できる設計 |
| 長期 | 第8次全銀システムの更改スケジュールとあわせ、現行が担う役割の一部を新システムへ移すことも検討 |

### 事前口座確認とは

送金を実行する前に、受取人の口座が実在し、名義が依頼人の想定と一致するかを確認する仕組みです。
英国の Confirmation of Payee、欧州の Verification of Payee などで導入されており、
**誤送金や詐欺（なりすまし口座への送金）の抑止** を目的とします。現行の全銀システムでは、名義相違は着信後に被仕向銀行が判断して返却します（→[第8章](08_returns_and_recalls.md)）。

## 10.4 将来像を模擬システムで考える

本模擬システムは現行の仕組みを再現していますが、拡張課題として次のような実験が考えられます。

| 拡張課題 | ヒント |
|---|---|
| 事前口座確認 | 送金前に被仕向銀行へ「口座照会電文」を送り、名義を返す。`bank.py` に照会ハンドラ、`telegram.py` に新しい電文種別を追加 |
| 着金確認 | 被仕向銀行の入金完了を仕向銀行に通知する電文を追加し、`TxStatus` に反映 |
| 常時 RTGS 型 | 小口も1件ごとに即時決済した場合、必要な日銀当預がどれだけ増えるか（`center._execute_small` を RTGS に差し替えて比較） |
| ISO 20022 | 模擬電文を XML（pacs.008 等の構造）で表現し、固定長との違いを比較 |
| 送金上限 | 新システム Day1 の上限を `config` に追加し、超過分は現行システムへ回すルーティング |

## 10.5 まとめ — 全銀システムを貫く設計思想

1. **通知は即時、資金は後で** — 利用者には即時性、銀行には流動性効率
2. **大口は RTGS、小口はネッティング** — リスクの大部分を消しつつ効率を維持
3. **CCP と3段構えのリスク管理** — 限度額・担保・流動性供給で決済完了を確保
4. **RC による接続の標準化** — 多様な勘定系を一つのネットワークに
5. **段階的な進化** — 8年周期のレベルアップ、モアタイムの追加、そして新システムとの併存
